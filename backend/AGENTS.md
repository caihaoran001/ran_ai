## Architecture — the big picture

改后端业务代码前先读本节，理清上下游数据流，再动局部。

### Messaging is layered (channel-agnostic core)
Message handling is split into three layers so business logic never touches a specific channel's API:
```
app/services/channels/     MessageChannel protocol, channel registry, QiWe adapter
app/services/ranren_ai/    RanrenAIEngine — channel-agnostic business engine
app/services/qiwe_service/ QiWe group-message aggregation
```
A QiWe callback turns inbound text into a `ChannelMessage`, aggregates consecutive messages from the same user/group over an ~8s window, then hands it to `RanrenAIEngine` (engine.py). The engine handles the intake-questionnaire command, risk/intervention analysis, and message persistence; the actual reply is generated by a **LangGraph ReAct agent** (`app/services/agent/graph.py::generate_agent_reply`, agent⇄tools two-node graph with a tool-call cap), which owns knowledge retrieval and other tool use. **To send messages, always go through the `channels` abstraction — never call a channel API directly.**

### Reply generation is an agent (`app/services/agent/`)
`generate_agent_reply` runs a `StateGraph` (agent node ⇄ tools node) over `base_model.bind_tools(...)`. The model may emit `<no_reply>` to stay silent. Before sending, the engine re-checks staff-took-over / newer-inbound guards and drops the reply if stale.

聊天 agent 能拿到的外部信息分**两类**：

**① 每轮自动注入**（不调工具，`run()` 拼进提示词）：当前北京时间（`_current_time_context`）；本轮用户消息 + 说话人 + 近期群聊；**隐性用户背景**（`profile_memory_service` 把 `UserProfile` + `UserStateProfile` + `ArchivistCaseMemory` 压成"结论小抄"：稳定事实/历程小结/长期偏好/稳定习惯/当前状态/最近话题/风险边界，每域最多 5 条取最新、每行≤120字）；skill 目录（仅名字+简介）。**完整带证据的 `state_json` 档案不再给 agent 查**——结论已在隐性背景里；完整档案给人从 `/users/{id}` 页面看。

**② 按需调工具**（22 个，`agent/tools/`）：
- 服务单只读 7 个（`_is_data_tool`，查不到走安全兜底不编造）：`get_service_progress`、`get_recent_checkins`、`get_weight_trend`、`list_delivery_documents`+`read_delivery_document`、`list_group_files`+`read_group_file`。
- 知识库 1 个：`search_knowledge_base`（RAG，见下）。
- 定时提醒 3 个：`create_group_reminder`/`list_group_reminders`/`cancel_group_reminder`（定时任务自身触发那次运行会关掉，`include_reminder_tools=False`，防提醒套提醒）。
- 打卡追问偏好 2 个：`get_checkin_followup_preferences`/`update_checkin_followup_preferences`。
- 五项追问清单 3 个：`get_checkin_checklist`/`set_checkin_checklist`/`restore_default_checkin_checklist`（设置/恢复只接受当前群已识别工作人员同一条消息明确 @ 机器人；清单独立版本化，不依赖系统发送文件）。
- 服务生命周期 3 个：`set_service_start_date`/`continue_service`/`end_continued_service`（只能由当前群聊显式 @ 机器人的消息触发；开始日期控制 28 天按天任务且不依赖问卷，续服沿用原服务天数、不新建周期）。
- 技能 2 个：`skill`（读 SKILL.md 全文）/`read_skill_file`。
- 联网 1 个：`web_search_lifestyle`（Tavily，硬拦健康/身体指标/隐私类，每轮≤2 次）。

### Knowledge retrieval / RAG (two-tier with fallback)
`search_knowledge_base` → `retrieve_indexed_knowledge`（`knowledge_index.py`）查 DB 索引 `knowledge_chunks`，命中正文交给 LLM。**检索不按 `source_type` 过滤**——所以**参考问答对（`faq`/`knowledge_draft`）和优秀案例（`case`）都在同一张表里一次混合检索返回，不分开**；另有 markdown fallback 素材（`markdown`）。检索用向量（pgvector）+ 关键词（pg_trgm ILIKE）双路 RRF 融合；embedding key 未配则仅走关键词。DB 索引全空时 fallback 到本地 Markdown/LlamaIndex 关键词检索（`backend/src/app/services/knowledge_base/`），且仅限业务白名单 `keyword_whitelist.json`——别拿每个 jieba token 都去查库。
- **注意**：`retrieve_case_context_db`（专门只查 `source_type='case'`、带 skill 教练头的独立优秀案例检索）已定义但**当前无任何调用点**（未接线）；优秀案例目前只能靠上面的混合检索被顺带捞到，没有独立案例通道在跑。要恢复"案例专用检索"需显式接线，别以为它在生效。

### Documents & profiles
Questionnaire submission → LLM generates a user profile. Service-case detail can generate two delivery docs (处方单, 28天执行单) and stage reports (3/7/14/21/28-day). The 28-day point ends the current service phase and does not generate a separate graduation report. Flow: LLM emits **structured JSON** for key fields → backend templates (`document_templates.py`) render editable Markdown → persisted as `content_json`/`content_md` → only at download/send time does `docx_service.py` render a temporary `.docx` (deleted after). **The authoritative system prompts live in `backend/src/app/services/document_service.py`; `手动版提示词.md` is reference only and must not be used at runtime.**

### Archivist — outcome / check-in / knowledge extraction (NOT per-message, NOT on the reply path)
成效抽取**不在消息主链路上实时跑**。消息进来只负责入库/回复；结构化抽取由独立的「档案官」`app/services/archivist/` 承担，在 **scheduler 进程** (`ran-ai-scheduler`) 里周期扫描完成：

- **触发** (`archivist/trigger.py::run_archivist_scan`)：`reminder_service.check_archivist_once` 按 `reminder_check_interval_seconds` 周期调用。**DB 派生找候选服务单 + 行锁防双跑**（重启不丢，不用内存 timer）。闸门：仅当累积 delta 含关键类目（可结构化打卡 / 稳定个人事实 / 阶段成效）且用户停说约 3min 才走 Fast 快触发；无增量则 `no_delta` 跳过。
- **抽取** (`archivist/graph.py`)：普通 async 流水线（load_context → extract → commit）。`extract` 单轮调用挂载 `report_*` schema 的模型，**只上报不落库**；候选校验和落库由后续确定性代码做。模块名保留 `graph.py` 仅为兼容既有导入。
- **产物**：① 刷新 `case_memory`（案例记忆）；② delta 抽出的 FAQ 候选转待审核 qa 草稿；③ **成效出现稳态变化时才合成优秀案例草稿**（代替原 day3/7/14/21/28 里程碑硬扫）。`outcome_engine.py` 退化为被档案官调用的成效抽取/评分工具，`user_state_profile.py` 仍把 outcome 投影为 JSONB `user_state_profiles`（action_focus / need_analysis / body_feedback / risk_profile），AI 回复引用当前 action focus 作隐性背景。
- 打卡追问 (`archivist/followup.py`) 由外部确定性触发：每 case 每天最多一条，共用 `ReminderEvent(rule_id="checkin_followup")` 天闸（见 memory「打卡追问线上已开启」）。

### Risk control
MVP risk is identified by **LLM intent/info extraction**, not hardcoded keywords. High-risk users never auto-receive AI content (forced human review); only the preset high-risk safety script may send immediately. Content policy (`content_policy.py`): `manual_review` (default — AI content goes to human review) vs `auto_send` (low-risk auto-sends, high-risk still reviewed).

### Auth model
Backend admin `/api/*` requires header `X-Admin-API-Key` (`BACKEND_ADMIN_API_KEY`); `/health` and public questionnaire (token-based) are exceptions. The admin key lives **only** between the Next server and FastAPI — never expose it to `NEXT_PUBLIC_*` or browser code. The frontend proxies backend API same-origin.

## CONVENTIONS

- 所有数据库操作使用 async/await
- 路由函数返回 SQLAlchemy 模型，FastAPI 自动序列化
- 依赖注入使用 `Depends(get_session)`
- 配置通过 `pydantic-settings` 管理
- 后端管理 API 默认需要 `X-Admin-API-Key`，公开问卷和 `/health` 是例外
- 软删除使用 `deleted_at` 字段，查询时需过滤 `deleted_at.is_(None)`
- 消息发送使用 `channels` 抽象层，不直接调用具体通道 API

## ANTI-PATTERNS

- 不要使用同步数据库调用 (`session.query()`)
- 不要直接修改已提交的迁移文件
- 不要在路由中直接调用 AI，使用 services 层
- 不要直接调用具体通道 API，使用 `channels` 抽象层
- 不要硬删除数据，使用软删除 (`deleted_at`)
- 不要把 `BACKEND_ADMIN_API_KEY` 暴露到 `NEXT_PUBLIC_*` 或浏览器端代码
