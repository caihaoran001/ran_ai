# 燃人AI 1.0 PRD（开发需求说明）

> 用途：指导开发与联调的单一需求基线。描述“应建成什么”，不是交付证明，也不是测试报告。
> 证据口径：每条需求标注【已核实】（有代码实现为证）或【待确认】（未在当前调用链中找到写入路径，或需产品决策）。
> 旧稿纠正：服务单状态不是一条必须依次走完的直线，而是按分支流转；`documents_generated`、`approved` 在生成流程内未写入，仅运营手动修改路径可写，见【待确认】。

## 1. 背景与目标

燃人AI 1.0 是内部社群运营系统：一个群对应一位真实用户的一段 28 天服务窗口。系统承载入营信息收集、用户画像与交付文件生成、人工审核、群内问答、打卡与阶段回顾、知识维护和基础运营视图。

目标：

- 同一群的服务过程可追溯：问卷、画像、文件、审核动作、聊天、打卡、阶段结论各自留痕。
- 生成与发送分离：模型只产出初稿，是否发给用户由人工规则决定。
- 状态可解释：服务单处在哪个阶段、为什么处在这个阶段，能从记录中找到原因。

非目标：

- 不承诺具体运营效果（减重结果、续费率、人效倍数）。
- 不规定模型品牌、模型参数与提示词原文。
- 不替代测试用例与部署手册。

## 2. 用户与角色

| 角色 | 做什么 | 不做什么 |
|---|---|---|
| 群内用户 | 填写入营问卷，群内交流，查看收到的文件 | 不操作系统后台 |
| 运营/班主任 | 跟进服务单，审核文件并确认发送，处理退款与续服，维护知识 | 不直接改数据库状态 |
| 管理员 | 配置问卷，查看运营视图，处理转人工事项 | 不绕过审核发送规则 |
| 系统 | 收发群消息，生成画像与文件初稿，执行提醒与归档 | 不代替人工做最终发送决策 |

## 3. 核心概念

### 3.1 群与服务单

- 一个群同一时刻只有一张“在场”服务单；客户退群后旧单让位，同群可开新一期，旧单留档。【已核实：`backend/src/app/models/service_case.py:65-70` 唯一索引，`backend/src/app/services/service_case_activation.py:140-174`】
- 群类型区分历史群与新流程群；入营问卷提交可把历史群升级为新流程群。【已核实：`backend/src/app/api/routes/questionnaires.py:158-167`】
- 删除为软删除（置 `deleted_at`），不物理删除。【已核实：`backend/src/app/api/routes/service_cases.py:275-306`】

### 3.2 服务单状态（分支，非直线）

枚举共 9 个取值【已核实：`backend/src/app/models/service_case.py:38-48`】：

`created`、`questionnaire_submitted`、`generating`、`documents_generated`、`reviewing`、`approved`、`in_service`、`completed`、`refunded`

实际流转是分支，不是必须依次经过 9 站：

| 分支 | 路径 | 证据 |
|---|---|---|
| 入营提交 | 前置态 → `generating`，并置“待生成”信号 | `questionnaires.py:158-185` |
| 生成成功 | 前置态 → `reviewing`（画像与两份交付文件同一事务落库） | `document_service.py:212-226` |
| 生成失败/资料待确认 | 先回到 `questionnaire_submitted`，问卷记录保留，备注写明原因，可重试；例外：若计划开始日期已到，回写后会被激活逻辑直接置为 `in_service` | `questionnaires.py:639-657`、`service_case_activation.py:85-100` |
| 到期激活 | 前置态 → `in_service`（计划开始日期到达，由调度器执行） | `service_case_activation.py:37-55` |
| 期满 | `in_service` → `completed` | `reminder_service.py:466-488` |
| 客户退群 | 仅 `in_service` → `completed`，并记审计 | `service_case_activation.py:140-174` |
| 本人回群 | 同时满足三条件才 `completed` → `in_service`：当前已完结、最后审计为“因退群自动结束”、28 天窗口未走完 | `service_case_activation.py:177-203` |
| 续服 | `completed`（且符合续服条件）→ `in_service` | `service_lifecycle_tools.py:192-261` |
| 退款 | 疑似退款先进入待确认，人工确认后才置 `refunded` | `models/service_case.py:159-161` |

【待确认】`documents_generated` 与 `approved` 作为服务单状态：生成流程内无写入，仅运营手动修改服务单接口可写（`api/routes/service_cases.py:246-272` 直接落值）。新开发不得假设这两个状态一定会出现，产品需确认是补齐流转还是移除该取值。

防倒退规则：已进入 `in_service`、`completed`、`refunded` 的服务单，不接受前置态回写。【已核实：`service_case_activation.py:85-100`】

### 3.3 28 天窗口

- 周期常量为 28 天。【已核实：`service_case_queries.py:15-18`】
- 计时起点优先用计划开始日期；打卡首日与服务首日的起算方式不同，联调时以实现为准。【已核实：`service_case_queries.py:21-57`】
- 续服中的服务单不受 28 天截止自动结束。【已核实：`service_case_queries.py:77-93`】

### 3.4 文档状态（与服务单状态区分）

交付文件有自己的状态：`draft`、`reviewing`、`approved`、`sent`、`archived`、`superseded`。【已核实：`models/user_document.py:32-40`】

- `archived`：人工审核后决定不发送，留痕（前端可显示“未发送”）。
- `superseded`：重新生成时被新版自动替代的旧稿，不是人工决定；已发送/已归档文件不被动。
- 每次新生成保留不可变首稿快照，运营编辑只改当前稿。【已核实：后端架构说明文档、画像与安全计算节】

## 4. 主流程

1. 建单：群内首条有效消息建单，初始 `created`。
2. 入营：用户提交入营问卷，只做数据库写入，置 `generating` 与待生成信号，不在请求路径跑模型或发消息。【已核实：`questionnaires.py:178-185`】
3. 生成：后台消费待生成信号，生成画像与两份交付文件（《个人能量重启诊断报告》《28天高燃人生执行建议书》，以 `document_common.py:19-22` 为准），同一事务落库后置 `reviewing`。
4. 审核发送：人工审核通过后发送；需复核或高风险不得自动发送。
5. 在服：进入 `in_service`，提供打卡、提醒、阶段报告、知识问答。
6. 完结分叉：期满完结、续服延长、退款确认、退群收口，见 3.2。

## 5. 功能需求

### 5.1 入营问卷

| 使用条件与操作 | 预期结果 |
|---|---|
| 用户填写完整必填内容并提交 | 提交成功，运营可查看该用户的答案；问卷记录保留 |
| 提交时服务单处在前置态 | 服务单置 `generating` 并留下待生成信号 |
| 重复提交（按模板策略） | 按模板规则拒绝或允许，不产生重复待办 |
| 运营编辑已提交的入营答案 | 答案更新，可重新触发生成；已发送旧文件保留 |

### 5.2 画像与交付文件生成

| 使用条件与操作 | 预期结果 |
|---|---|
| 待生成信号存在 | 生成用户画像 1 份与两份交付文件 |
| 问卷信息完整 | 文件中的姓名、目标等与问卷一致；不编造问卷未提供的健康事实 |
| 模型服务不可用或资料待确认 | 问卷不丢失；先回到 `questionnaire_submitted` 并留下原因备注；例外：计划开始日期已到时会被激活为“服务中”，运营侧以服务单实际状态为准；运营可识别并重试 |
| 重新生成 | 新文件进入待审核；旧草稿/待审核稿自动标记为被替代；已发送与已归档文件不动 |

### 5.3 人工审核与发送

当前运营方式：文件发送默认仍由运营手动触发；自动发送开关存在，但默认处于关闭状态。开启自动发送后，低风险文件会绕过人工点击，因此在启用自动发送前，必须先把文档状态与退群动作的闸门补上。

| 使用条件与操作 | 预期结果 |
|---|---|
| 文件被标记需人工复核 | 未经人工确认不得自动发送 |
| 服务单为高风险 | 不得自动发送模型内容；按预设安全口径处理并提示联系运营 |
| 审核通过并确认发送 | 文件送达用户群，发送结果留痕；运营确认即代表对所选版本负责，已归档与被替代版本同样可被选中发出，选中前须自行核对 |
| 审核不通过 | 文件归档留痕，不发送；原因可追溯 |

### 5.4 服务开始

| 使用条件与操作 | 预期结果 |
|---|---|
| 已设置的服务开始日期到达 | 服务进入“服务中” |
| 未填问卷或文件未审核 | 不得因此阻止到期激活；问卷不是激活前置条件【已核实：`service_case_activation.py:13-24` 注释】 |

### 5.5 群内问答与知识

| 使用条件与操作 | 预期结果 |
|---|---|
| 用户在群内提问 | 结合知识库生成回复；保留用户原话，不用改写替代对话 |
| 知识库命中参考问答 | 回复与命中内容一致；分类、风险、转人工字段不混入检索正文 |
| 用户表达放弃、强烈不满等 | 按受挫场景检索成功案例或转人工，不混用普通问答 |
| 本地素材未启用 | 不得作为运行时兜底直接引用；须先列入启用清单并同步入库 |

### 5.6 打卡

| 使用条件与操作 | 预期结果 |
|---|---|
| 聊天与问卷产生结构化记录 | 按天归档，不依赖 `#打卡` 文本格式 |
| 同一服务单同一日期重复扫描 | 仅保留一条有效记录，不重复落库 |
| 运营查看打卡 | 按白名单字段展示；完整度按既定口径判定 |

### 5.7 阶段报告

| 使用条件与操作 | 预期结果 |
|---|---|
| 到达 3/7/14/21/28 天阶段点 | 可生成对应阶段报告；内容含阶段总结、风险提醒与后续建议 |
| 28 天结束 | 不再额外生成“毕业报告”类型（该类型仅兼容历史记录）【已核实：`models/user_document.py:17-29`】 |

### 5.8 提醒

| 使用条件与操作 | 预期结果 |
|---|---|
| 到达提醒时间且当日未满足提醒条件 | 发送提醒；同一天不重复 |
| 客户已退群 | 停止该群一切自动动作 |

### 5.9 知识维护

| 使用条件与操作 | 预期结果 |
|---|---|
| 运营新增或编辑 FAQ | 启用后同步到检索索引，禁用后不再参与检索 |
| 模型提炼候选知识 | 必须经人工批准才入库，不直接写文件 |
| 关键词兜底检索 | 仅使用业务白名单命中词 |

### 5.10 运营视图

| 使用条件与操作 | 预期结果 |
|---|---|
| 查看服务单、画像、文件、聊天、打卡、阶段状态 | 各模块对同一事实（姓名、目标、打卡项、风险状态）展示一致 |
| 查看统计 | 口径按实现为准：全站统计面向新流程群、按单计数；“在服”需人在群；新增用户按问卷提交时间；转人工看风险标记；毕业与提前结束按结束日期划分 |

## 6. AI 内容规则

- 问卷提交后先做安全信息提取与确定性事实计算，再生成画像与文档；安全边界不依赖模型自由发挥。【已核实：后端架构说明】
- 交付文档先产出结构化数据，再由模板渲染正文并持久化；下载或发送时才临时渲染文档格式。
- 内容不得编造问卷未提供的饮水、疾病、情绪等事实；不得输出医疗诊断、治疗建议与疗效承诺；风险、退款、退出场景按规则转人工。
- AI 回复质量不按固定措辞验收；验收看事实一致、回应相关、不编造、风险按规则处理。样例与通过门槛需另行明确，不在本 PRD 内虚构。

## 7. 非功能约束

- 鉴权：后端管理接口使用管理员密钥；健康检查与公开问卷为例外；密钥不得进入浏览器代码。【已核实：后端架构说明风控节】
- 数据：禁止物理硬删除；观测写入失败只告警，不改变业务结果。
- 通道：核心业务只收统一渠道消息，出站统一经通道抽象；入站先持久化再处理，出站先记录再请求再回写结果。
- 媒体：单次获取有大小上限，大文件按区间续传拼齐；原图持久化保存，数据库只存路径与描述。
- 性能与容量数字（如响应时长、并发上限）不在本 PRD 内承诺；如业务需要，须先明确测试条件与目标值。

## 8. 验收标准

下表是“做到什么算满足需求”，不是“已经测试通过”。

| 功能 | 使用条件与操作 | 预期结果 |
|---|---|---|
| 入营问卷提交 | 填写完整必填内容并提交 | 提交成功且运营可查；提交成功与文件生成完成分开显示 |
| 文件生成 | 基于已提交入营信息生成 | 生成画像与两份交付文件；关键信息与问卷一致，不编造未提供信息 |
| 生成失败 | 模型不可用或资料待确认 | 问卷保留，不显示成功；运营可识别原因并重试（计划开始日已到时状态可能直接为“服务中”，以实际状态为准） |
| 审核发送 | 文件需复核或服务单高风险 | 未经人工确认不得自动发送；运营可查看、修改、确认发送 |
| 服务开始 | 计划开始日期到达 | 进入“服务中”；不以前置问卷或审核为前提 |
| 打卡归档 | 聊天与问卷增量到达 | 按天仅一条有效记录；不依赖文本关键词格式 |
| 知识入库 | 新增 FAQ 或批准草稿 | 启用后可检索，禁用后不可检索；未批准不入库 |
| 退群与回群 | 客户退群 / 本人回群 | 退群收口并停自动动作；回群仅在三条件齐备时恢复 |
| 退款与续服 | 识别疑似退款 / 申请续服 | 退款先待确认后人工确认；续服按规则延长在服 |

验收方法与测试操作见测试用例文档，不在本 PRD 内展开；实际是否通过以测试记录为准。

## 9. 待确认事项

1. 服务单 `documents_generated`、`approved` 取值的去留：补齐流转还是移除取值（当前仅手动路径可写，生成流程内未写）。
2. 可选加固（仅当保持人工发送时可推迟）：发送前拦已归档/被替代版本、生成与发送前检查退群标记；若启用自动发送，这些闸门变为必要前提。
3. 打卡白名单字段的最终清单与必填口径。
4. 提醒时间、 weekdays 与节假日策略。
5. 内容质量样例库与通过门槛。
6. 运营视图统计口径如需调整，以产品决策为准，调整后同步更新本 PRD。
