# 可复用测试用例清单

**用途**：供 OpenCode / AI Agent / 开发者按固定口径执行测试。
**性质**：这是可复用测试用例，不是某次历史执行结果。每次实际执行结果必须另写 `test-execution-YYYY-MM-DD-HHMM.md` 和 `test-summary-YYYY-MM-DD-HHMM.md`。
**总入口**：执行前必须先读 `docs/testing/README.md`。

---

## A. 安全健康自测（诊断控制台 01-08）

目标：验证核心流程通畅，不调用真实 LLM，不向真实群发消息，测试数据回滚。

| ID | 范围 | 最低验收 |
|---|---|---|
| HC-01 | 入营问卷 | 问卷提交、画像生成、两份交付文档创建成功；确定性事实不丢失 |
| HC-02 | 聊天风控 | 普通、高风险、退款、续购、拒绝机器人继续解释等场景能得到正确状态 |
| HC-03 | 打卡 | 打卡创建、结构化字段、排序与展示一致 |
| HC-04 | 阶段报告 | 3/7/14/21/28 天和毕业报告生成链路可用 |
| HC-05 | 知识进化 | FAQ/案例草稿生成、审核入库、知识块同步可用 |
| HC-06 | 策略开关 | 文档发送、AI 回复、知识进化、软删除等开关生效 |
| HC-07 | QiWe 通道 | 聚合、幂等去重、问卷指令、发送失败兜底不破坏回调 |
| HC-08 | 成效引擎 | 成效提取、阶段状态、行动焦点、时间感知追问可用 |

必须记录：

- 诊断控制台是否显示 `01-08` 连续编号。
- `E2E-01` 是否独立显示，且未被安全健康自测自动执行。
- 若失败，记录具体套件、命令、关键日志和是否有业务数据残留。

## B. 契约与内容准确性测试

目标：验证同一事实在不同模块中的表达一致，避免“流程通了但内容错了”。

| ID | 契约 | 最低验收 |
|---|---|---|
| CT-01 | 入营问卷 → 画像 → 文档 | 姓名/称呼、性别、年龄、身高、体重、BMI、腰围、减重带、28天目标不冲突 |
| CT-02 | 文档打卡项一致性 | 《28天执行标准》最终 Block 7 = `profile.personalized_checkin_fields` = 每日行动问卷 API 字段 |
| CT-03 | 打卡字段类型 | 含“是否”的字段为 RADIO，选项为“是/否”；评分/体重等非判断题为输入字段 |
| CT-04 | 最新文档优先 | 已有旧画像默认字段时，每日行动链接仍优先读取最新执行文档 |
| CT-05 | 文档口径一致 | 处方单与执行标准的蔬菜、运动、睡眠、产品节律建议不互相矛盾 |
| CT-06 | 风险/人工介入一致 | 高风险、退款、投诉、拒绝机器人继续解释应在服务单、审核控制台、提醒中一致呈现 |
| CT-07 | 成效数据一致 | 成效事件、阶段状态、阶段快照、用户动态画像不互相矛盾；问卷提交应补齐建档类成效证据 |
| CT-08 | 成本统计 | 服务单成本与全局看板成本来自 `ai_usage_logs`，金额保留两位，token 数与调用数可追溯 |

最低抽样要求：

- 每次测试至少抽 1 个新建入营服务单做 CT-01 到 CT-04。
- 如本次改动涉及文档、画像、打卡、成效、审核、消息通道，必须执行相关 CT 项。

## C. Playwright 浏览器交互测试

目标：验证运营和用户真实页面操作。优先写成可重复执行的 Playwright spec；OpenCode 可以自主探索补充，但不能替代 spec 基线。

| ID | 页面/流程 | 最低验收 |
|---|---|---|
| PW-01 | 登录与导航 | Basic Auth 后可进入后台；侧栏导航到用户、审核、运营规则、看板、诊断台 |
| PW-02 | 入营问卷 | 打开 `/q/{token}`，填写/一键提交成功，重复提交显示已提交状态 |
| PW-03 | 每日行动链接 | 字段与最新执行文档 Block 7 一致；必填校验和提交成功状态可见 |
| PW-04 | 用户管理 | 正常/已删除切换、用户详情、已删除服务单访问不崩溃 |
| PW-05 | 服务单详情 | 问卷链接、聊天记录、打卡、交付文件、成效引擎、成本显示正常；聊天默认滚到最新消息 |
| PW-06 | 审核控制台 | 新待审核 AI 回复/文档/知识草稿出现后自动刷新；可审核通过/驳回/确认发送 |
| PW-07 | 运营规则配置 | AI 回复策略、文件发送策略、问卷发送计划、入营提交回执、提醒配置可保存并回显 |
| PW-08 | 数据看板 | 指标卡可点击 drill-down；诊断入口不干扰看板主信息 |
| PW-09 | 系统诊断 | 01-08 布局清晰；E2E-01 独立；运行时有进度、日志、成本和失败信息 |

执行要求：

- 页面加载通过和交互通过必须分开记录。
- 若缺少特定数据，先构造可回滚测试数据；不能简单标记“未测但应可用”。
- 截图或 trace 保存到本次执行报告引用的位置。

## D. 真实 LLM E2E（E2E-01）

目标：验证真实模型下的全链路质量。只能在用户明确授权或诊断控制台二次确认后运行。

当前覆盖：

- 十类问卷起点用户：积极配合、焦虑、沉默不配合、轮班、咖啡因敏感、平台期、退款、慢病用药、续营、低落恢复。
- 一条完整 28 天闭环：阶段报告、知识进化、FAQ/案例审核、向量召回、毕业报告。
- 质量评审：一次 LLM-as-a-Judge 综合评审，对话质量、文档准确性、风险意图、打卡成效四维评分。

最低验收：

- 十类用户独立事务，某一类失败不得阻断其余人设执行。
- 任一评分子项 < 3 即失败；违规等级只解释原因，不单独作为失败条件。
- 业务测试数据回滚；真实 LLM token、成本、耗时作为诊断记录保留。
- 报告必须记录 diagnostic_run_id、调用次数、token、成本、耗时、失败人设和失败维度。

## E. Mock Time / 定时任务测试

目标：验证提醒、阶段报告、成效快照等时间触发逻辑。

建议归属：

- 不单独新建大文件，优先放入现有相关套件：
  - 成效快照/阶段状态：`test_08_outcome_engine.py`
  - 消息通道提醒或打卡提醒：`test_06_toggles.py` 或后续拆出的 `test_09_reminders.py`
- 只在时间触发场景明显增多时，再拆独立 reminder 测试文件。

最低验收：

- 使用 monkeypatch/freezegun 等方式控制当前时间。
- 覆盖工作日/周末、时区、同日不重复、超过阈值触发、未超过阈值不触发。
- 不能依赖真实等待。
