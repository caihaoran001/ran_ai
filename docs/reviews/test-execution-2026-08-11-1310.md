## 6. 失败证据

### 6.1 Token 截断修复已验证

- 上一轮 26 条统一报 `IncompleteOutputException: ... max_tokens length limit`。
- 本轮 50 题全部获得终态，`errors=0`，没有任何 `max_tokens`、API 参数、OOM 或容器异常。
- 判官实际环境为 50,000；这只是最大允许输出，并不代表每次固定生成或计费 50,000 tokens。

### 6.2 Answer Relevancy 存在明显校准问题

- 35 条应检索题全部低于 0.80，最高值仅 0.798。
- 有 5 条题的召回率、精确率和忠实度全部过线，唯一失败原因仍是 Answer Relevancy。
- “瓶盖和刻度换算”回答直接给出“一瓶盖不够、3 小刻度约两瓶盖”，但该项仅得 0.489。
- 因此不能把 36 条失败直接等同于 36 条业务回复错误；Answer Relevancy 的中文适配和 0.80 门槛需先用人工标注样本校准，不能直接为提高通过率而下调阈值。

### 6.3 两条关键事实冲突

| 用例 | 权威口径 | 实际回复问题 |
|---|---|---|
| `rag-faq-meal-order` | 先蛋白质，再蔬菜，最后主食 | 先给出正确顺序，随后又说“先吃两口菜再吃肉也问题不大” |
| `rag-chat-meal-order-why` | 同上 | 说“你习惯先吃菜也行”，软化并反转了要求的先后关系 |

两条都被独立关键事实检查标为 `critical_fact_contradiction`，没有被均值掩盖。

### 6.4 六条检索决策错误

- 应检索却跳过 5 条：午B超过最晚时间是否补喝、产品与额外咖啡因叠加、喝后手抖是否代表代谢启动、要求统一瓶盖/刻度标准、两天未排便并求助。
- 应跳过却检索 1 条：查询当前已设置的提醒。这属于实时系统操作，应该交给回复 Agent 的服务单工具，不应查通用知识。

### 6.5 瓶盖翻车案例

固定题库中有两个相关用例：

1. `rag-faq-cap-conversion`
   - 改写：明确询问一盖是否够一大刻度。
   - 召回：命中 `1 瓶盖≈1.5 小刻度`、`1 大刻度=3 小刻度≈两瓶盖`。
   - 回复：明确“一瓶盖不够”，召回率/精确率/忠实度均为 1.0。
   - 最终失败仅因 Answer Relevancy=0.489。
2. `rag-chat-cap-ambiguity`（原真实翻车消息）
   - 原问题：`瓶盖一盖就可以了吗`，上下文已给出晚A一大刻度和三小刻度。
   - 实际改写：`瓶盖的一盖是否可以代替瓶体小刻度来计量产品用量？`，没有误解成“盖上瓶盖”，但仍未显式补全“晚A + 一大刻度”，改写不够完整。
   - 双路召回都命中正确换算知识；最终明确回答“一瓶盖不够，约需两瓶盖，300ml 温水”，没有反转数字或比较方向。
   - Context Recall=1.0、Precision=1.0、Faithfulness=0.778、Answer Relevancy=0.633，最终因后两项低于阈值而失败。
