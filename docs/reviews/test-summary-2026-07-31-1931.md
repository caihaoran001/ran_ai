## 一、结论

权限恢复后，真实 `deepseek-v4-flash` 测试已经实际跑到模型响应阶段。结论很明确：

- 安全因子小调用可用，健康场景未误判，孕期场景正确进入人工复核。
- 明显腰高比矛盾的确定性生成前闸门可用，`ready=false`、中文原因和零模型调用均正确。

## 二、发现的问题

### Critical｜生产文档模型 Flash 无法稳定形成正式交付文件

生产运行配置当前把 `AI_DOCUMENT_MODEL` 也设为 `deepseek-v4-flash`。真实样例中，完整文档生成没有一次通过；失败发生在正式画像/文档落库之前，因此不会下发半份文件，但新问卷提交可能持续停留在生成失败状态，需要运营重试或人工处理。

这不是本次 V2.2 目标公式、腰高比闸门或动态五项代码本身的失败，而是当前文档模型与大输出 schema 的适配问题。

### Major｜仅提高 token 上限不能证明能解决

两次截断说明 16000 token 不够，但另一次在未触发截断时仍未形成可识别的两份文档结构。因此单纯提高 `AI_MAX_TOKENS` 可能增加延迟和费用，却仍无法保证 schema 合规。

### Minor｜临时测试夹具腰围字段键首次写错

该错误导致一次不必要调用，发现后已中断并用正确字段零调用复测。它不影响前两个 Flash 完整生成失败结论，但“腰高比偏高而非矛盾”的真实模型场景本轮没有完成最终文档验证。

## 三、流程与内容正确性

- 网络、Docker、生产 SSH 和 DeepSeek API 全部通畅，本轮失败不是环境阻塞。
- 确定性生成前阻断流程正确，未生成半份正式文件。
- 安全因子内容合理，没有编造风险，孕期原因准确。
- 完整用户画像、两份文档、人工复核 D7 文案、A 带无数字和动态五项均因模型输出失败而无法进入最终用户可见内容评审。

## 四、建议

**暂不建议让生产文档链路继续使用 Flash 承担这个大 package。**

风险最低的方案是保持聊天与风险识别使用 Flash，仅把 `AI_DOCUMENT_MODEL` 恢复为 `deepseek-v4-pro`；代码已经支持独立文档模型，不需要改业务逻辑。随后用相同两个样例重新验证。

如果必须坚持全量 Flash，则需要先缩减一次性输出 schema，或拆分画像与两份文档生成，再做真实模型回归。仅把 16000 调大不应直接上线。

## 五、生产处置建议

V2.2 代码已在生产，本结论不是建议回滚这些确定性规则；但当前上线版本不能按“真实文档生成验收通过”处理。生产 `AI_DOCUMENT_MODEL=deepseek-v4-flash` 的真实文档生成为 `0/3` 可用，属于交付主链路阻塞。

恢复自动文档生成的可用验收，至少需先完成以下一项：

1. `AI_DOCUMENT_MODEL` 改回 Pro，并让本轮两个完整样例通过；或
2. Flash 生成链路完成缩减/拆分，并通过相同内容与一致性检查。
