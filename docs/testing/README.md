# 燃人AI 测试执行规范

本文档是 AI Agent、OpenCode 和开发人员执行项目测试时的唯一入口。

当用户只说“测试”“完整测试”或“检查当前项目”时，必须按照本文档执行。默认任务是**测试与报告**，不是修复代码。

具体测试用例固定在 `docs/testing/TEST_CASES.md`。执行测试时必须同时阅读：

1. `docs/testing/README.md`
2. `docs/testing/TEST_CASES.md`

本文件回答“怎么测、边界是什么、报告怎么写”；`TEST_CASES.md` 回答“具体测哪些用例”。

执行者定位：

- 仓库命令和 repo spec 负责可重复回归。
- OpenCode 自带 Playwright MCP 负责自动页面交互与截图取证。
- 人只负责授权真实 E2E 或确认是否修复，不参与手工点页面替代测试。

## 一、默认边界

默认完整测试必须满足：

- 不修改业务代码、测试代码、配置文件或测试预期。
- 不调用真实消息通道，不向真实群发送消息。
- 默认不自由调用真实 LLM；所有常规测试均使用 Mock 机制。
- 不永久保留测试数据；自动化测试应回滚或清理数据。
- 不把历史 `docs/reviews/` 文件中的“通过”当作本次测试结果。
- 发现失败后继续执行其他可独立测试项，并在本次测试记录中如实记录。

以下操作必须先获得用户明确授权：

- 调用真实 DeepSeek/Qwen/Embedding API 做质量评估。
- 向 QiWe 或其他真实消息通道发送消息。
- 永久提交测试服务单、聊天、打卡、知识草稿或向量数据。
- 修改代码来修复测试失败。

## 二、测试分层

### A. 诊断控制台测试

用途：快速判断核心流程是否仍然通畅。

要求：

- 页面“一键安全健康自测”显示为连续编号 `01-08`，测试核心流程。
- 使用 Mock AI 和 Mock 消息通道。
- 测试结束后无业务数据残留。
- 重点检查接口、状态流转、数据落库、审核策略和通道适配。
- 不以“接口返回 200”代替业务断言。

诊断控制台只是快捷入口，不代表内容质量已经通过。

### B. 契约与内容准确性测试

用途：检查不同模块对同一事实是否保持一致，避免“各自正确、组合错误”。

必须重点验证：

1. 入营问卷确定性事实、用户画像、两份交付文档之间不冲突。
2. 《28天执行标准与打卡要求》的最终 `content_json.blocks` 中每日打卡项，与：
   - 画像中的 `personalized_checkin_fields`
   - 群发每日行动链接 API 返回字段
   - 字段类型、选项、必填状态
   完全一致。
3. 最新执行文档必须优先于旧画像中的通用默认打卡项。
4. BMI、减重带、姓名/称呼、28 天目标等跨模块字段保持一致。
5. 审核/自动发送配置与最终消息、文件状态保持一致。
6. 高风险、退款/退出意向、人工介入等状态能在服务单、审核控制台和提醒中一致呈现。
7. 成效事件、阶段状态、阶段快照和用户动态画像之间不互相矛盾。

内容准确性测试不仅检查数量和字段存在，还必须比较最终用户可见内容。

### C. 浏览器交互测试

用途：验证用户和运营人员实际能否完成操作。

优先使用 Playwright。至少覆盖：

- 问卷打开、填写、提交、已提交状态。
- 每日行动链接展示最终执行文档定义的打卡项。
- 审核控制台出现新待审核内容并自动刷新。
- AI 回复审核、文件审核和知识草稿审核操作。
- 服务单、用户画像、成效追踪和聊天记录展示。
- 删除用户与已删除服务单访问。

仅验证“页面能加载”不能视为交互流程通过。

### D. 内容质量评审

用途：判断 LLM 内容是否合理、自然、安全，而不只是 JSON 结构合法。默认全部由 LLM-as-a-Judge 自动完成，不引入人工步骤作为测试通过条件。

自动评审层必须检查：

- 不编造问卷中未提供的饮水、暴食、风险、疾病或情绪事实。
- 用户画像与两份交付文档的判断、目标和建议不冲突。
- 交付文档内容不过度繁琐，格式与参考文件接近。
- 群聊回复能利用上下文，不机械复读，不重复已经完成的流程。
- 不出现医疗诊断、治疗建议、中医辨证、疗效承诺或不必要的恐吓。
- 风险场景、退款意向和强续购意向能正确转人工。

评分阈值：

- 每项评分为 1-5 分，任何子项 < 3 即视为该维度不通过。
- 违规按严重度分级：`minor` / `major` / `critical`，仅用于解释低分原因，不再作为独立的失败条件。

### E. 真实 LLM 全链路测试（已废弃）

由于真实大模型测试耗时较长、开销较大且容易因随机生成而产生测试抖动，全链路真实模型端端测试已全面废弃，相关代码已从项目中移除。目前系统的所有功能流程和逻辑均由 `01-08` 阶段的 Mock 自动化自测套件覆盖。

## 三、默认完整测试执行顺序

### 1. 记录环境与工作区

```bash
git status --short
git log -1 --oneline
docker compose ps
```

记录当前 commit、未提交改动和服务状态。不得还原或覆盖用户现有改动。

### 2. 后端静态与自动化测试

```bash
TEST_TS="$(date +%Y-%m-%d-%H%M%S)"
mkdir -p docs/reviews/artifacts
cd backend
PYTHONPYCACHEPREFIX=/tmp/ran_ai_pycache uv run python -m compileall src scripts
uv run pytest tests -q \
  --junitxml="../docs/reviews/artifacts/${TEST_TS}-pytest.xml"
```

必须记录：

- 收集的测试数量。
- 通过、失败、跳过数量。
- 测试结束后的 warning/asyncpg 异常噪声。
- 是否存在后台任务异常被吞掉的风险。

### 3. 前端类型检查

```bash
cd frontend
npx tsc --noEmit --incremental false
npm run test:e2e -- --list
```

`npm run test:e2e -- --list` 用于确认仓库内 Playwright spec 可被发现。若前端服务已启动且浏览器依赖已安装，再执行：

```bash
cd frontend
npm run test:e2e
```

默认 Playwright 配置读取：

- `PLAYWRIGHT_BASE_URL`，默认 `http://127.0.0.1:3002`
- `ADMIN_USERNAME` / `ADMIN_PASSWORD`，用于后台 Basic Auth

若未安装浏览器或前端服务未启动，必须在检查记录中标记为“环境阻塞”，不得把 `--list` 写成完整浏览器交互通过。

### 4. 契约与内容准确性检查

自动化测试后，必须额外核对本次改动相关的用户可见内容。

对于跨模块功能，至少抽取一个真实结构样例，比较上游输入、中间存储和最终用户可见输出。不能只检查字段存在或接口状态码。

打卡链路的最低检查标准：

```text
执行文档最终 Block 7
  = 用户画像 personalized_checkin_fields
  = personalized_checkin 问卷 API 字段
```

比较内容必须包括：顺序、标题、类型、选项和 required。

### 5. 浏览器检查

若浏览器工具可用，执行与本次改动相关的核心页面检查。检查记录必须区分：

- 页面加载通过。
- 交互操作通过。
- 因缺少测试数据未执行。

不得把页面加载通过写成完整交互通过。

## 四、测试报告要求

本节是项目测试报告格式的唯一来源。每次按本文执行测试时，`docs/reviews/` 只新建一个三行 Markdown 索引；测试产物和执行明细统一放在 `docs/reviews/artifacts/`。历史报告不修改。

### 1. 后端 pytest XML

默认完整测试的后端 pytest 必须生成 JUnit XML，文件名为 `docs/reviews/artifacts/<时间>-pytest.xml`。本规范的完整测试命令会先进入 `backend/`，因此必须使用上一级路径：

```text
cd backend
mkdir -p ../docs/reviews/artifacts
uv run pytest tests -q \
  --junitxml=../docs/reviews/artifacts/<时间>-pytest.xml
```

`<时间>` 在实际执行前替换为本次执行时间，例如 `2026-09-14-153000`。如果从项目根目录执行等价命令，路径应改为 `docs/reviews/artifacts/<时间>-pytest.xml`。专项 pytest 可使用带场景后缀的独立 XML 文件，避免覆盖同一批次的结果。XML 只记录 pytest 结果，不能用它代替其他检查的结果，也不能伪造 XML。

### 2. 非 pytest 检查记录

编译检查、前端类型检查、Playwright、OpenCode MCP 以及 API/数据库核对等非 pytest 检查，统一写入一个简短的文本制品：

```text
docs/reviews/artifacts/<时间>-checks.txt
```

该记录必须包含执行前的 commit、工作区状态和服务状态，以及实际运行的每条命令、执行方式、每项的状态（通过 / 失败 / 跳过 / 未执行 / 环境阻塞）和关键证据；失败要留下可复现信息，页面加载与交互结果要分开写。截图、trace 等文件的路径也写在这里。还要注明是否调用真实 LLM、是否产生费用、是否保留数据。没有执行的检查也要写明原因，不得把检查结果写成不存在的 XML。

### 3. 三行 Markdown 索引

每次测试在 `docs/reviews/` 只新建一个索引文件，例如：

```text
test-index-YYYY-MM-DD-HHMMSS.md
```

索引必须严格只有三行：

```text
提交：<git commit>
结论：通过 <数量>；失败 <数量>；跳过 <数量>；未执行 <数量>；环境阻塞 <数量>；关键失败：<没有则写“无”>
制品：<按实际生成填写，例如 docs/reviews/artifacts/<时间>-pytest.xml；docs/reviews/artifacts/<时间>-checks.txt；其他截图或 trace 路径>
```

第二行必须包含全部五种状态和关键失败；没有对应制品时不填写虚假路径。详细命令、范围、未覆盖内容、根因判断、影响范围和发布建议写入 `-checks.txt`，不再创建旧的两份长 Markdown 报告。

禁止：

- 用“已执行用例通过率 100%”掩盖大量未执行项。
- 把历史报告的结果直接复制为本次结果。
- 把“测试发现了生产 Bug”描述成“测试逻辑问题”。
- 在没有可重复执行证据时标记为通过。

## 五、发现失败后的默认动作

1. 保留失败现场并继续执行其他独立测试。
2. 不修改业务代码或测试预期。
3. 在 `-checks.txt` 中写明根因判断、影响范围和建议修法。
4. 向用户汇报测试结论，等待用户明确要求修复。

只有用户明确说“修复”“改吧”“实现修复”后，才能进入代码修改流程。
