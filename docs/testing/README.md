# 燃AI 测试执行规范

本文档是 AI Agent、OpenCode 和开发人员执行项目测试时的唯一入口。

当用户只说“测试”“完整测试”或“检查当前项目”时，必须按照本文档执行。默认任务是**测试与报告**，不是修复代码。

## 一、默认边界

默认完整测试必须满足：

- 不修改业务代码、测试代码、配置文件或测试预期。
- 不调用真实消息通道，不向真实群发送消息。
- 默认不自由调用真实 LLM；真实 E2E 仅通过诊断控制台 `E2E-01` 或用户明确授权运行。
- 不永久保留测试数据；自动化测试应回滚或清理数据。
- 不把历史 `docs/reviews/` 文件中的“通过”当作本次测试结果。
- 发现失败后继续执行其他可独立测试项，并在报告中如实记录。

以下操作必须先获得用户明确授权：

- 在命令行直接运行 `backend/tests/test_e2e_01_real_llm.py`。
- 调用真实 DeepSeek/Qwen/Embedding API 做质量评估。
- 向 QiWe 或其他真实消息通道发送消息。
- 永久提交测试服务单、聊天、打卡、知识草稿或向量数据。
- 修改代码来修复测试失败。

## 二、测试分层

### A. 诊断控制台测试

用途：快速判断核心流程是否仍然通畅。

要求：

- 页面“一键安全健康自测”显示为连续编号 `01-08`，不会运行真实模型 E2E。
- 真实模型测试单独显示为 `E2E-01`，必须在“真实模型验证”区域确认后运行；黑窗口中应显示 `tests/test_e2e_01_real_llm.py`。
- 使用 Mock AI 和 Mock 消息通道。
- 测试结束后无业务数据残留。
- 重点检查接口、状态流转、数据落库、审核策略和通道适配。
- 不以“接口返回 200”代替业务断言。

诊断控制台只是快捷入口，不代表内容质量已经通过。

### B. 契约与内容准确性测试

用途：检查不同模块对同一事实是否保持一致，避免“各自正确、组合错误”。

必须重点验证：

1. 入营问卷确定性事实、用户画像、两份交付文档之间不冲突。
2. 《28天执行标准与打卡要求》的最终 `content_json.blocks` 中每日打卡项，与：
   - 画像中的 `personalized_checkin_fields`
   - 群发每日行动链接 API 返回字段
   - 字段类型、选项、必填状态
   完全一致。
3. 最新执行文档必须优先于旧画像中的通用默认打卡项。
4. BMI、减重带、姓名/称呼、28 天目标等跨模块字段保持一致。
5. 审核/自动发送配置与最终消息、文件状态保持一致。
6. 高风险、退款/退出意向、人工介入等状态能在服务单、审核控制台和提醒中一致呈现。
7. 成效事件、阶段状态、阶段快照和用户动态画像之间不互相矛盾。

内容准确性测试不仅检查数量和字段存在，还必须比较最终用户可见内容。

### C. 浏览器交互测试

用途：验证用户和运营人员实际能否完成操作。

优先使用 Playwright。至少覆盖：

- 问卷打开、填写、提交、已提交状态。
- 每日行动链接展示最终执行文档定义的打卡项。
- 审核控制台出现新待审核内容并自动刷新。
- AI 回复审核、文件审核和知识草稿审核操作。
- 服务单、用户画像、成效追踪和聊天记录展示。
- 删除用户与已删除服务单访问。

仅验证“页面能加载”不能视为交互流程通过。

### D. 内容质量评审

用途：判断 LLM 内容是否合理、自然、安全，而不只是 JSON 结构合法。默认全部由 LLM-as-a-Judge 自动完成，不引入人工步骤作为测试通过条件。

自动评审层必须检查：

- 不编造问卷中未提供的饮水、暴食、风险、疾病或情绪事实。
- 用户画像与两份交付文档的判断、目标和建议不冲突。
- 交付文档内容不过度繁琐，格式与参考文件接近。
- 群聊回复能利用上下文，不机械复读，不重复已经完成的流程。
- 不出现医疗诊断、治疗建议、中医辨证、疗效承诺或不必要的恐吓。
- 风险场景、退款意向和强续购意向能正确转人工。

评分阈值与违规分级：

- 每项评分为 1-5 分，任何维度 < 3 即视为不通过。
- 违规按严重度分级：`minor` / `major` / `critical`。
- 出现 `critical` 违规，或累计超过 2 个 `major` 违规，直接视为测试失败。

### E. 真实 LLM 全链路测试

仅在用户明确授权后执行。运行前必须说明：

- 会调用真实模型并产生费用。
- 可能耗时较长。
- 业务测试数据会回滚；真实模型 token、费用和耗时会作为诊断记录单独保留。
- 是否会调用真实消息通道。

`backend/tests/test_e2e_01_real_llm.py` 当前包含十类问卷起点用户旅程，以及一条覆盖知识进化和结营报告的完整 28 天旅程。所有模拟客户业务数据都回滚，不进入用户列表、数据看板或知识库；真实模型的 token、费用和耗时作为诊断成本单独保留。

真实 E2E 采用“十类用户旅程 + 完整闭环 + 自动化内容评审”的覆盖方式：

- 十类用户都从填写入营问卷开始，逐日推进 28 天；没有消息或打卡的日子代表真实沉默行为。每类用户使用独立测试事务，某类失败后其余人设仍会继续执行。
- 当前覆盖积极配合、焦虑、沉默不配合、轮班、咖啡因敏感、平台期质疑、退款、慢病用药、续营、低落恢复；活跃用户旅程必须包含连续多日聊天，不能只用 2-3 条消息代表 28 天服务。
- 确定性断言检查问卷、画像、两份文档、每日行动字段、风险、提醒、成效事件和追问时机。
- LLM 质量评审按维度拆分检查对话质量、文档准确性、风险意图判断、打卡与成效提取；评审输入应包含完整对话、完整交付文档和全部结构化打卡，不得只截取最后几条。
- 完整闭环旅程继续验证阶段报告、知识进化、FAQ/案例审核和向量召回。

## 三、默认完整测试执行顺序

### 1. 记录环境与工作区

```bash
git status --short
git log -1 --oneline
docker compose ps
```

记录当前 commit、未提交改动和服务状态。不得还原或覆盖用户现有改动。

### 2. 后端静态与自动化测试

```bash
cd backend
PYTHONPYCACHEPREFIX=/tmp/ran_ai_pycache uv run python -m compileall src scripts
uv run pytest tests --ignore=tests/test_e2e_01_real_llm.py -q
```

必须记录：

- 收集的测试数量。
- 通过、失败、跳过数量。
- 测试结束后的 warning/asyncpg 异常噪声。
- 是否存在后台任务异常被吞掉的风险。

### 3. 前端类型检查

```bash
cd frontend
npx tsc --noEmit --incremental false
```

若项目已有可重复执行的 Playwright 测试，再执行对应脚本；若没有，必须在报告中明确写“仓库内无可重复执行的 Playwright 用例”，不得用旧人工记录代替。

### 4. 契约与内容准确性检查

自动化测试后，必须额外核对本次改动相关的用户可见内容。

对于跨模块功能，至少抽取一个真实结构样例，比较上游输入、中间存储和最终用户可见输出。不能只检查字段存在或接口状态码。

打卡链路的最低检查标准：

```text
执行文档最终 Block 7
  = 用户画像 personalized_checkin_fields
  = personalized_checkin 问卷 API 字段
```

比较内容必须包括：顺序、标题、类型、选项和 required。

### 5. 浏览器检查

若浏览器工具可用，执行与本次改动相关的核心页面检查。测试报告必须区分：

- 页面加载通过。
- 交互操作通过。
- 因缺少测试数据未执行。

不得把页面加载通过写成完整交互通过。

## 四、测试报告要求

每次测试必须在 `docs/reviews/` 新建两个文件：

```text
test-execution-YYYY-MM-DD-HHMM.md
test-summary-YYYY-MM-DD-HHMM.md
```

### 执行记录必须包含

- 当前 commit 和工作区状态。
- 实际运行的每条命令。
- 每项测试的状态：通过 / 失败 / 跳过 / 未执行 / 环境阻塞。
- 关键输出、失败证据和可复现步骤。
- 是否调用真实 LLM、是否产生费用、是否保留数据。

### 总结报告必须包含

- 本次测试范围与明确未覆盖范围。
- 发现的问题，按严重程度排序。
- 流程通畅性结论。
- 内容正确性与业务合理性结论。
- 是否建议发布，以及该建议依赖哪些尚未验证的假设。

禁止：

- 用“已执行用例通过率 100%”掩盖大量未执行项。
- 把历史报告的结果直接复制为本次结果。
- 把“测试发现了生产 Bug”描述成“测试逻辑问题”。
- 在没有可重复执行证据时标记为通过。

## 五、发现失败后的默认动作

1. 保留失败现场并继续执行其他独立测试。
2. 不修改业务代码或测试预期。
3. 在报告中写明根因判断、影响范围和建议修法。
4. 向用户汇报测试结论，等待用户明确要求修复。

只有用户明确说“修复”“改吧”“实现修复”后，才能进入代码修改流程。
