# 燃人AI 1.0 产品白皮书（对外介绍）

> 读者：投资人、合作方、非技术业务方。
> 用途：讲清产品是什么、给谁用、怎么用、能力边界在哪。不含开发需求细节，不含运营效果承诺。
> 数据说明：本文件不引用具体客户数量、转化率、收入、人效等经营数字；如需对外披露，须另行提供经核实的口径与时间范围。

## 1. 一句话介绍

燃人AI 1.0 是面向社群健康服务的运营辅助产品：一个服务群对应一位用户的一段 28 天服务旅程，系统负责收集信息、生成个性化文件初稿、跟进打卡与阶段回顾，人工负责审核与关键决策。

## 2. 解决什么问题

- 社群服务高度依赖人工盯群：信息散在聊天里，画像、计划、打卡、回顾靠人工整理，容易遗漏。
- 用户信息跨环节易断裂：问卷填过的内容，聊了几天就对不上；换人跟进要重新问。
- 自动化与人工缺分工：要么全人工盯不过来，要么全自动不敢放手，风险内容无人把关。

产品思路：让系统做收集、整理、初稿与跟进，让人工做审核、发送与例外决策；全过程留痕，可回看。

## 3. 服务谁

- 使用方：提供 28 天制社群健康服务的运营团队（运营、班主任、管理员）。
- 服务对象：群内接受服务的用户。
- 不面向：直接面向消费者的独立 App；本产品运行在运营后台与服务群之内。

## 4. 28 天服务旅程

以一次完整的服务为例：

1. 建群接入：用户进群，系统建立该群的服务单，开始留痕。
2. 入营收集：用户填写入营问卷，留下基本信息、目标与注意事项；运营可查看答案，必要时修正。
3. 画像与文件初稿：系统根据已提交信息生成用户画像与两份交付文件初稿——《个人能量重启诊断报告》讲判断与建议，《28天高燃人生执行建议书》讲每天做什么、怎么打卡。
4. 人工审核与发送：运营检查初稿，修改确认后发送给用户；需要复核或存在风险的内容不会自动发出。
5. 每日执行：用户按文件行动，聊天与问卷中的结构化记录按天归档为打卡；运营可查看进展。
6. 阶段回顾：在 3/7/14/21/28 天节点生成阶段报告，总结进展、提示风险、给出后续建议。
7. 结营分叉：期满正常结束；符合条件可续服；涉及退款走人工确认；用户退群则收口停更。

## 5. 产品能力

- 入营问卷：公开链接填写，答案结构化保存；运营可编辑已提交答案并重新触发生成。
- 画像与交付文件：基于已提交信息生成初稿；关键信息与问卷保持一致；每次生成保留初稿快照，修改留痕。
- 人工审核：审核、修改、发送、归档动作完整；风险内容设闸门，未经确认不发出。
- 群内问答：结合知识库回答用户问题；知识分“参考问答”与“成功案例”两类使用场景。
- 打卡：按天归档，不依赖固定文本格式；重复处理不会产生重复记录。
- 阶段报告：按阶段点生成，服务单详情可查看阶段状态与最近动态。
- 提醒：到点提醒、当天不重复；用户退群后停止自动动作。
- 知识维护：运营可维护 FAQ；模型提炼的候选知识须经人工批准才入库。
- 运营视图：服务单、用户、文件、聊天、打卡、阶段结论集中查看；统计口径统一，避免各处说法不一。

## 6. 人机分工

| 系统做 | 人做 |
|---|---|
| 收集问卷与聊天增量，整理成结构化记录 | 审核文件初稿，决定发与不发 |
| 生成画像、文件、阶段报告初稿 | 修改初稿中的判断与措辞 |
| 到点提醒，按天归档打卡 | 处理退款、续服、投诉与例外 |
| 检索知识并起草群回复 | 把关风险内容，必要时接管对话 |

原则：模型只产出初稿；面向用户的正式结论与发送动作一定经过人工或既定闸门。

## 7. 知识如何沉淀

- 运营维护的 FAQ 启用后进入检索，停用后退出。
- 聊天中沉淀的候选经验先进入草稿，人工批准后才成为正式知识。
- 检索正文与管理字段分离：用户看到的是问法与回复，分类与风控标记只用于内部管理。
- 本地素材先登记启用再同步入库；未启用的历史材料不参与线上问答。

## 8. 安全与边界

- 问卷提交后先做安全信息提取与事实计算，再生成文件；安全判断不交给模型自由发挥。
- 内容不编造用户未提供的信息；不输出诊断、治疗与疗效承诺类表述。
- 高风险、退款、退出等场景按规则转人工。
- 用户数据软删除、不物理抹除记录的前提下按权限查看；对外介绍不披露任何真实用户信息。
- 性能、容量与效果数字不在本文件承诺；合作前须另行明确测试条件与目标。

## 9. 典型使用场景

- 新用户入营：发问卷链接 → 收答案 → 出画像与两份文件初稿 → 审核发送。
- 日常跟进：看打卡 → 群内答疑 → 到点提醒 → 异常转人工。
- 阶段复盘：到节点出阶段报告 → 调整计划 → 留档。
- 人员交接：新运营接手时，看服务单全链路记录即可 continuity，无需重新问用户。
